## Abstract

Three separate teams within our organization independently hit out-of-memory failures in PyTorch 2.0.1 training loops lasting more than 48 hours. The failures correlated with custom data-loading code that retained references to intermediate tensors across mini-batches. We characterize the leak, show that it is not reproducible in synthetic benchmarks, and document the practical `torch.cuda.memory_snapshot()` workflow that let us localize the issue.

## Methods

Environment: PyTorch 2.0.1 + CUDA 11.8, NVIDIA H100 80GB and A100 80GB. Training frameworks: one team using raw PyTorch loops, one PyTorch Lightning 2.0.7, one HuggingFace Trainer. All were training 7B-parameter transformers on multi-GPU (4–8 GPU) setups with DDP.

Memory tracking: `torch.cuda.memory_allocated()` sampled every 100 steps; `torch.cuda.memory_snapshot()` captured at step-0, step-10k, step-50k, step-100k.

## Results

Team A (raw loop): memory usage drifted from 68 GB → 79 GB over 85k steps, then OOM at step 89,412. The leak localized to a list of attention maps retained for logging; once the training outgrew the 16 GB safety margin, OOM was deterministic.

Team B (Lightning): OOM at ~120k steps. Cause: custom callback that appended batch tensors to a list without detaching or moving to CPU. Memory snapshot showed 3.2 GB of leaked `torch.Tensor` objects held by Python reference.

Team C (HuggingFace Trainer): OOM at ~200k steps, but only with `gradient_accumulation_steps=4`. The leak was in a custom `compute_metrics` function retaining prediction tensors on GPU between accumulations.

The common pattern: each team's leak was in *their* code, not PyTorch's. The shared root cause was misunderstanding that `.detach()` does NOT free GPU memory — only `.cpu()` or going out of scope does.

## Discussion

We built a minimal reproducer and confirmed that stock PyTorch 2.0.1 does not leak on a pure forward/backward loop over 1M steps (memory stable within 40 MB). All observed leaks were in custom instrumentation code.

Common patterns to avoid: (1) appending GPU tensors to Python lists for logging — always `.cpu().detach().numpy()` first; (2) custom schedulers holding `model.state_dict()` snapshots without detaching; (3) caching tokenizer output in-memory without bounded LRU.

We also observed that `torch.compile()` interacts with these leaks unpredictably — leaked tensors retain the compiled graph, which can hold 2-3× more memory than the tensor itself. Turn off compile when debugging memory issues.

The `torch.cuda.memory_snapshot()` visualizer (use the `torch._C._cuda_attach_out_of_memory_observer` API) was essential for localizing these bugs — 10 minutes with the snapshot tool beats 3 hours of print-debugging.
